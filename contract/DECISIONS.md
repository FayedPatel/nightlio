## Permanent contract facts

Flask is gone, so nothing "drifts" from it anymore — these are simply how the API behaves, promoted from the old "accepted drift" / "residual serialization drift" lists to first-class contract facts on 2026-08-16 and pinned by tests where a silent regression is possible. Historical Flask behavior is noted only so old recordings and fixtures aren't surprising.

### Path-id parsing

1. **Out-of-range path ids (> i64) return a clean 404**, exactly like negative and non-integer ids — the route simply never matches. (Flask 500'd here with leaked Python `OverflowError` text; the recorded fixture documents that history.) Pinned by the int-converter tests in `api/tests/shell_router.rs`.

### Contract encoding facts

How responses are encoded on the wire. No client parses these byte-level details (JSON is parsed, not byte-compared), but they are pinned so they cannot silently change:

- JSON bodies are compact serde_json output — no pretty-printing, no trailing newline. (Flask appended a newline and pretty-printed in debug.) Test: `json_bodies_are_compact_without_trailing_newline` in `api/tests/shell_router.rs`.
- Non-ASCII is emitted as raw UTF-8, never `\uXXXX` escapes (same decoded value; Flask escaped). Test: `non_ascii_content_is_raw_utf8_not_escaped` in `api/tests/mood_routes.rs`.
- Login Set-Cookie carries `Max-Age` and omits the redundant `Expires` attribute (Max-Age is authoritative per RFC 6265); attribute order is unspecified. Test: `assert_session_cookie` in `api/tests/auth_family.rs` grades the full attribute set including `Expires` absence.
- The JWT verifier accepts integer `exp`/`iat` only — float claims are rejected (stricter than python-jose; no live-token impact since only ints were ever issued). Test: `float_exp_iat_token_is_invalid_here_though_jose_accepts_it` in `api/src/auth/jwt.rs`.
- Requests without an `Origin` header get no `Access-Control-*` headers at all (they are not CORS requests; browsers always send Origin on CORS requests). Test: `originless_request_gets_no_cors_headers` in `api/tests/shell_router.rs`.
- Float JSON values are parsed correctly rounded and re-serialize byte-identically (serde_json's `float_roundtrip` feature; the default parser is 1-ulp imprecise on full-precision floats, which would silently perturb REAL mood values and epoch timestamps on the way in). Test: the pinned round-trip in `json_bodies_are_compact_without_trailing_newline`.
- JSON key order is unspecified and may differ from old Flask recordings on `/statistics/heatmap`, `/statistics/digest`, `/api/moods`. Untested on purpose — key order carries no meaning.
- 405 `Allow` joins methods comma-only (recorded as-is in `time_post_405.json` since 2026-08-16 — contract, not drift; method order may differ from Werkzeug's).

## contract changes (owner-approved, executed 2026-08-24)

- **New authenticated `data` family — versioned JSON export/import (v0.6.0).** Two new rules (registered-rule count 48 → 50), both behind require_auth: `GET /api/export/data` returns the portable v1 envelope `{schema_version: 1, exported_at, app_version, data: {entries, goals}}` as the JSON response body (the frontend builds the downloadable file), and `POST /api/import/data` accepts the same envelope as plain `application/json` (no multipart) and merges it. This closes the README roadmap's last unchecked item (Data Import/Export). Like i18n, the family is Rust-native: it never existed in Flask, so the 15 fixtures in `contract/fixtures/data/` are **hand-authored spec, not recordings** — the contract the implementation is graded against, and frozen goldens from now on. Specifics pinned by the fixtures and the OpenAPI fragment:
  - **The envelope carries NO ids and NO user_id.** Autoincrement ids are not portable across instances (fresh DBs pre-seed 3 default groups / 27 options; the login upsert burns rowids). Entry selections are denormalized by exact name as `{group_name, option_name}` pairs; import resolves-or-creates groups and options by name (`idx_groups_user_name` unique; `group_options` deduped via a preloaded name cache). File timestamps are preserved on import via `COALESCE(?, CURRENT_TIMESTAMP)`. Export order is deterministic and contract: entries ascending by date, goals in creation order; selections in the `GET /api/mood/{id}/selections` order (group name, then option name).
  - **Merge-skip semantics.** Import runs inside ONE transaction, rows in file order. Entries dedupe on the `(date, content)` pair; goals dedupe on `title`, and a duplicate goal is skipped WHOLE — its completions are ignored, so an import never mutates existing streak/weekly state. The dup set is updated after each insert, so intra-file duplicates skip too. Completions of a NEW goal insert with `INSERT OR IGNORE` semantics. The 200 body is exactly `{"status": "success", "entries": {"imported": N, "skipped": M}, "goals": {…}}` — integer counts, never echoed rows. Re-importing the same file is idempotent (everything skips).
  - **Atomic whole-file 400.** Any invalid row rejects the entire file with a row-indexed message (`entries[1]: mood must be between 1 and 5`) and NOTHING commits — the fixture `import_data_post_400_invalid_row.json` pins the atomicity, not the text (message text stays ungraded app-wide; only the two CSRF 403 strings are fixed). Merge-skip makes the retry free: fix the row, re-POST the whole file.
  - **No side effects.** Import performs NO achievement checks and writes NO activity_log rows — it is a pure restore, not replayed user activity (a restored year of entries must not unlock `week_warrior` or flood the activity feed). Export is a pure read: goal weekly state is exported with the rollover *projected* exactly as the goals GETs project it, persisted never; import writes that state raw and lets `project_rollover` self-heal stale periods on the next read.
  - **`schema_version` dispatch.** The importer reads `schema_version` before anything else: missing → 400; anything but a known version → 400 `Unsupported schema_version: N (supported: 1)`. Importers accept every version ≤ their current one, so v1 files import forever; unknown extra JSON keys inside a supported version are ignored (future additive fields never break old files — version bumps are reserved for breaking changes). Policy + field tables live in `docs/EXPORT-FORMAT.md` (normative).
  - **Caps and routing.** In-handler body cap 8 MiB (8388608 UTF-8 bytes) → 413, the `MAX_PDF_CONTENT_SIZE` pattern (code-derived, no fixture); transport-level body limit 16 MiB. Everything else conforms to the app-wide rules, fixture-pinned: 401 before any body validation (the `export_pdf_post_401` precedent), cookie-auth CSRF 403s with the exact strings, strict-slash 404s, unified 405 envelope + `Allow` on `GET /api/import/data`, automatic OPTIONS 204 (`Allow` export `HEAD, GET, OPTIONS`, import `OPTIONS, POST`) answered before any token check. A non-JSON body under Bearer takes the app-level 400 `{"error": "Bad request"}` — the import parser is strict, never `get_json(silent=True)`-lenient.

  Moved together: `contract/fixtures/data/` (15 fixtures: `export_data_get_200`, `export_data_get_200_empty`, `export_data_get_401`, `export_data_options_204`, `export_data_get_trailing_slash_404`, `import_data_post_200` — one duplicate + one new per category, seeding order in its note — `import_data_post_200_all_new_empty_db`, `import_data_post_400_missing_schema_version`, `import_data_post_400_unsupported_schema_version`, `import_data_post_400_invalid_row`, `import_data_post_400_not_json`, `import_data_post_401`, `import_data_post_403_cookie_missing_csrf`, `import_data_options_204`, `import_data_get_405`); the new fragment `contract/openapi-parts/data.yaml`; the merged `contract/openapi.yaml` (paths `/api/export/data` + `/api/import/data`, schemas `DataExport`/`DataExportEntry`/`DataExportSelection`/`DataExportGoal`/`DataImportResult`, plus a Global-rules bullet — path count 39 → 41, operations 52 → 54, auth'd-rule count 33 → 35, with the path/operation totals restated in `contract/README.md`); `src/types/api.ts` (the same five type names); `docs/EXPORT-FORMAT.md` (normative format doc); the two `docs/DEVELOPMENT.md` API-reference rows; and `api/tests/data_routes.rs`, which replays these fixtures against both backends.

## contract changes (owner-approved, executed 2026-08-22)

- **New unauthenticated `/api/i18n` family (hot-swappable language packs, v0.6.0).** Two new GET-only rules (registered-rule count 46 → 48): `GET /api/i18n/languages` → `{"languages": [{code, name, native_name, version}]}` (object envelope, sorted by code ascending, empty array when nothing is cached) and `GET /api/i18n/{code}` → the pack envelope `{schema_version: 1, language, name, native_name, version, strings: {nested string tree}}` or the standard app-level 404 for an uncached code. Both are **unauthenticated** — they must be reachable pre-login, and no 401/403 path exists on this family. The family is Rust-native: it never existed in Flask, so the eight fixtures in `contract/fixtures/i18n/` are **hand-authored spec, not recordings** — they are the contract the implementation (landing in the next phase) is graded against, and they are frozen goldens from now on like every other fixture. Specifics pinned by the fixtures:
  - **Caching contract.** The pack 200 carries the strong validator `ETag: "<code>-<version>"` plus `Cache-Control: public, max-age=3600` and honors `If-None-Match` (exact string compare, quotes included) with a **304**: empty body, no Content-Type, same ETag + Cache-Control. The browser HTTP cache is the caching layer (the service worker stays NetworkOnly for `/api/*`). The 304 amends the 2026-08-16 "sole empty-body response" fact: OPTIONS 204s aside, the `GET /api` 308 and the i18n 304 are now the only empty-body responses; neither is a 2xx, so the frontend's throw-on-non-JSON-2xx rule is untouched.
  - **The languages list carries `Cache-Control: public, max-age=3600` and NO ETag** (owner decision): the `"<code>-<version>"` formula has no meaning for a multi-pack list, and any composite validator would be an implementation-defined hash impossible to record deterministically. Time-based caching suffices for a tiny JSON list.
  - **English is never listed.** `/api/i18n/languages` omits `en` even when an en pack is cached; the frontend unions bundled English into its picker. `GET /api/i18n/en` still serves a cached en pack — that is how English itself stays hot-swappable (typo fix = new `lang-en-v*` release, no redeploy). On a cold cache every code 404s and clients run on bundled English; upstream (GitHub) failures never surface on these routes (serve-stale-forever, or the empty state).
  - **Routing conforms to the app-wide rules**, fixture-pinned: trailing-slash variants 404 with the JSON envelope; POST → unified 405 envelope + axum comma-joined `Allow`; OPTIONS → automatic 204 empty with `Allow: HEAD, GET, OPTIONS`. `{code}` is an opaque string segment (no `<int:>` converter semantics); the static `languages` segment wins over `{code}`, making the code "languages" unreachable (harmless — no such language code).
  - **Pack `strings` is NESTED on the wire** (amended in place 2026-08-22 — the owner asked for nested end-to-end while the family was still unreleased, so this is an amendment to the same day's work, not a breaking change). The `strings` field mirrors the (already nested) `src/i18n/en.json` source catalog: each object key is one segment of the dot-path id and every leaf is a string, so `{"strings": {"nav": {"home": "Inicio"}}}` carries the id `nav.home`. Clients flatten the tree to dot-keys for lookup (`flat(pack.strings)[key] ?? en[key] ?? key`). Server-side validation accepts a flat dot-key map as the degenerate nesting (a top-level `"nav.home"` key flattens to the same id, so rejecting it would buy nothing) but never converts — packs are served exactly as validated, and the canonical form produced by the build pipeline and required of `I18N_LOCAL_DIR` files is nested. Non-string leaves (numbers, arrays, booleans, null) are rejected anywhere in the tree. Everything else about the family — the ETag formula, Cache-Control, 304, 404, English-never-listed, the 1 MiB cap — is unchanged. `contract/openapi.yaml` models the tree as the recursive `I18nStringsNode` schema.

  Moved together: `contract/fixtures/i18n/` (8 fixtures: `languages_get_200_empty`, `languages_get_200_with_packs`, `pack_get_200`, `pack_get_304_etag_match`, `pack_get_404_unknown`, `languages_get_trailing_slash_404`, `pack_post_405`, `languages_options_204`), the new fragment `contract/openapi-parts/i18n.yaml`, and the merged `contract/openapi.yaml` (paths `/api/i18n/languages` + `/api/i18n/{code}`, parameter `LanguageCode`, schemas `LanguagesResponse`/`LanguageInfo`/`LanguagePack`/`I18nStringsNode`, plus a Global-rules bullet — path count 37 → 39, operations 50 → 52). `src/types/api.ts` gains the i18n types together with the implementing workstream in the next phase (the shapes here are normative for it); route tests will replay these fixtures with wiremock faking the GitHub release discovery.

- **`GET /api/config` gains a `version` field.** The response now carries a fifth key, `version`: the server semver baked in at compile time via `env!("CARGO_PKG_VERSION")` (`api/src/routes/misc.rs`). Rationale (v0.6.0 cache-versioning work): the version cannot come from the git tag — publish.yml's retag job never rebuilds, so the tag re-points an image built before the tag existed; the committed crate version is the only truth the shipped binary can report. The fixture `contract/fixtures/misc/config_get_200.json` records it as the `"<VERSION>"` placeholder, substituted with the live `CARGO_PKG_VERSION` by `config_matches_fixture` in `api/tests/shell_router.rs` (same normalization pattern as `"<TS>"` timestamps) — future version bumps never touch the fixture. Moved together: `PublicConfig` gained a required string `version` in `contract/openapi.yaml` and `contract/openapi-parts/misc.yaml`; `info.version` bumped to 0.6.0; `scripts/check-version-sync.sh` (wired into `.github/workflows/test.yml`, which publish.yml gates on) asserts package.json, api/Cargo.toml, and openapi info.version stay in lockstep, with `scripts/bump-version.sh` as the convenience bumper.

- **`/api/v1` URL alias (v0.6.0 API versioning).** The entire route surface is additionally mounted under the `/api/v1` prefix: every registered rule answers byte-identically at its `/api/v1/...` path — including the slash pair (`GET /api/v1` 308-redirects to `/api/v1/`, always within its own prefix, never across) and the conditional OIDC rules (whose `redirect_uri` is unaffected: it is either the configured absolute `OIDC_CALLBACK_URL` or built from scheme + host with a hardcoded `/api/auth/callback/oidc` path in `api/src/auth/oidc.rs`, so the issuer-registered callback stays on `/api` regardless of arrival prefix). Implementation is a second registration of the same routers (`family_router()` / `misc::router_at(prefix)` in `api/src/routes/mod.rs` and `api/src/routes/misc.rs`), never a redirect between prefixes — a 308 from one prefix to the other was rejected because it breaks CORS preflights, and header-based versioning was rejected because it is invisible to the path-keyed fixture oracle. **`/api` stays the canonical, graded prefix**: all 189 golden fixtures are untouched and keep grading `/api`; alias behavior is spot-checked by six tests in `api/tests/shell_router.rs` (v1 health + middleware headers, v1 slash 308, v1 config byte-equality, nested-family 401, deep completions route, v1 JSON 404). The CORS / security-header / ProxyFix middleware applies post-assembly and covers the alias automatically, and nginx's `location /api/` already proxies `/api/v1/...` — zero nginx change. **The frontend switches to `/api/v1` no earlier than v0.7**: switching in the same release would break self-hosters who pull only one of the two images (a new frontend calling `/api/v1` against an old API, or vice versa, would pair mismatched halves). `contract/openapi.yaml` documents the alias in `info.description` only; paths are deliberately not duplicated under `/api/v1`.

## contract changes (owner-approved, executed 2026-08-17)

- **`POST /api/export/pdf` now requires auth.** The rule gained the `AuthUser` extractor (`api/src/routes/extras.rs`), so it behaves like every other protected mutation: no credentials → 401 `{"error": "Authorization header required"}` before any body validation; cookie-authenticated callers must also send `Content-Type: application/json` + `X-Requested-With: nightlio` or take the shared CSRF 403; Bearer callers bypass CSRF. The 200 / 400 / 413 bodies are byte-identical to before — only the credential requirement is new. Rationale: the rule was unauthenticated purely as Flask parity (Flask's route was missing `@require_auth`, which the old `SECURITY.md` flagged as a likely oversight and risk-accepted), leaving an unauthenticated CPU-and-memory DoS surface — repeated just-under-1-MiB renders — on any internet-exposed instance. The frontend (`ApiService.exportPdf`) has always sent the Bearer token / cookie plus the CSRF header, so no client breaks. Deliberately **not** rate-limited: once auth is required, request-volume abuse is an authenticated user's self-harm on a single-operator instance, and the 1 MiB content cap already bounds per-request cost. Moved together: new fixture `contract/fixtures/misc/export_pdf_post_401.json`; auth notes added to the three existing `export_pdf_post_*` fixtures; `security` + 401/403 on the operation in `contract/openapi.yaml` and `contract/openapi-parts/misc.yaml` (auth'd-rule count 32 → 33); `docs/DEVELOPMENT.md` API reference; tests `export_pdf_post_401_without_credentials`, `export_pdf_403_cookie_missing_csrf_header`, `export_pdf_200_through_router_with_bearer` in `extras.rs`. `src/types/api.ts` unchanged — the response shape did not move. This closes the last risk-accepted follow-up from the old v0.2.0 security pass (see `SECURITY.md`).

## contract changes (owner-approved, executed 2026-08-16)

The four remaining "permanent" Flask quirks (items 3/8/9/11) retired as deliberate contract changes; every touched fixture carries a "contract change" note, and OpenAPI (merged + parts), `src/types/api.ts`, and the frontend moved together:

- **#11 Goals weekly rollover moved out of GET.** `GET /api/goals`, `GET /api/goals/{id}`, and the completions existence probe are pure reads: the rollover (completed reset, streak recompute, `period_start` = current ISO Monday) is *projected* into the response and persisted only by the write paths (`POST /api/goals/{id}/progress`, `PUT`/`PATCH /api/goals/{id}`). Wire shapes are unchanged — only the DB write disappeared from reads (`api/src/db/goals.rs`: `project_rollover` / `persist_rollover_if_changed`). This also fixed a latent bug: `update_goal` previously never rolled over, so its `completed = MIN(completed, ?)` clamp operated on stale week state; it now persists the rollover first and clamps the rolled value (regression test `update_goal_rolls_over_stale_week_before_clamping`).
- **#9 Statistics GET purified; data_lover is per-day.** `GET /api/statistics` no longer increments anything. The new `POST /api/statistics/view` (200 `{"counted": bool}`, require_auth + CSRF like every mutation, strict-slash) records at most one view per user per server-local day (`user_metrics.last_view_date`); `data_lover` now means "view statistics on 10 different days". Existing `stats_views` counters were RESET to 0 by the migration (`PRAGMA user_version` 2→3, guarded `ALTER TABLE user_metrics ADD COLUMN last_view_date TEXT` + one-shot `UPDATE user_metrics SET stats_views = 0`); already-earned badges are kept (achievements rows untouched). Rationale: the old write-on-GET double-counted (frontend double-fetch: 2 increments/visit, 4 in dev StrictMode) and made fixture replay order-sensitive.
- **#8 `new_achievements` unified.** `POST /api/mood` returns metadata objects (`{achievement_type, name, description, icon, rarity}` — the same `NewAchievement` shape as `POST /api/achievements/check`, built by the shared `new_achievement_objects` helper) instead of bare `achievement_type` strings. `GET /api/achievements` is unchanged (full rows merged with metadata). Frontend only ever read `?.length` on the mood-response field, so no client broke.
- **#3 OPTIONS unified on 204.** Every route answers OPTIONS with 204, an empty body, and an `Allow` header (Content-Type `text/html; charset=utf-8` kept); the explicit 204 handlers (`completions_options`, `achievements_progress_options`) were deleted and the automatic handlers flipped 200→204. CORS preflights ride the same 204 via the non-short-circuiting after-request CORS layer. Wire 204s carry no `Content-Length` (hyper strips it). Fixtures re-recorded/renamed: `misc/preferences_options_204_plain.json`, `misc/preferences_options_204_cors_preflight.json`, `auth/verify_options-204.json`.
- **Corpus re-pins.** `contract/corpus/fresh.pragmas.txt`, `legacy-groups.migrated.pragmas.txt`, and `half-migrated.migrated.pragmas.txt` gained the `user_metrics.last_view_date` column row, and the expected `.migrated.db` / `fresh.db` goldens were regenerated to match the v3 schema (pristine inputs untouched; `.counts.txt` unchanged). Owner-approved schema migration per the standing corpus rule.

## Other owner decisions (executed 2026-08-16)

- **#2 405/308 bodies unified on the JSON envelope.** Every 405 returns `{"error": "Method not allowed"}` + `Allow` via a router-level `method_not_allowed_fallback`; the `/api/music/vibe` hand-dispatched Werkzeug-HTML 405 replica and the `GET /api` 308 "Redirecting..." HTML replica were deleted (308 keeps status + `Location`, empty body — the sole empty-body response). Rationale: the API was self-inconsistent — empty 405 bodies everywhere except one hand-written HTML route, while every other error uses the envelope; no client parses these bodies. Fixtures `time_post_405.json` / `health_get_no_trailing_slash_308.json` re-pinned with "contract change" notes; 405 body graded by tests in `shell_router.rs`, `extras.rs`, `goals.rs`.
- **WAL journal mode enabled, size-bounded.** Pooled connections set `journal_mode=WAL` with `wal_autocheckpoint` at the 1000-page default (~4 MB auto-fold) and `journal_size_limit=4194304` (the `-wal` file is truncated back to ≤4 MB after checkpoints — it cannot grow unboundedly). `checkpoint_truncate` runs after bootstrap and on graceful shutdown (SIGINT/SIGTERM), so the log starts at 0 bytes and disappears on clean stop. Bootstrap's raw connection and the parity goldens are untouched. Pre-v0.4.0-image rollback is formally retired; backup guidance updated in `docs/UPGRADING.md`.
- **Argon2 rehash-on-login adopted.** New hashes are argon2id (PHC format, RustCrypto defaults); legacy Werkzeug scrypt/pbkdf2 hashes keep verifying and are transparently re-stored as argon2id after the next successful login (rehash failure never fails the login). Verified live: werkzeug-seeded hash became `$argon2id$` after first login and kept verifying.
- **SSO ⇒ local login disabled (production operating model).** `DISABLE_LOCAL_LOGIN` defaults to the OIDC-configured state: with `OIDC_ISSUER_URL` set and the flag unset, `/api/config` reports `enable_local_login:false` and local login answers 403 `Local login is disabled`; explicit `0`/`1` always wins. Verified live in both directions. E2E harness (OIDC blanked) unaffected.
- **Pocket ID SSO verified live (human passkey).** Owner completed Pocket ID setup at `http://pocket-id.localhost:1411`, registered a passkey, created an OIDC client with callback `http://localhost:5173/api/auth/callback/oidc`, set `OIDC_ISSUER_URL`, and signed in end-to-end via "Sign in with SSO" through the Docker stack; the same run confirmed the OIDC auto-disable path above. Setup gotcha: the Pocket ID UI must be visited on the exact `APP_URL` origin (`pocket-id.localhost`, the WebAuthn RPID) — browsing via `127.0.0.1:1411` fails passkey registration with "Passkeys cannot be used on the configured domain".
- **#16 linux/arm64 publishing adopted.** `publish.yml` builds and pushes `linux/amd64,linux/arm64` for both images via `docker/setup-qemu-action` + full per-platform QEMU emulation (see `api/Dockerfile`'s top-of-file comment for why that beat `cross`/`cargo-zigbuild`). Locally verified on an amd64 host: arm64 image built under emulation (~29 min first build, dominated by rusqlite's bundled SQLite compile; cached afterward), `Architecture: arm64` confirmed, `uname -m` → `aarch64` in-container, `--health-check` exit 0, `GET /api/` 200 from a second container; the amd64 leg rebuilt and health-checked as a regression check.

## contract changes (owner-approved, executed 2026-08-15)

Former "bug-compatible" items fixed as deliberate contract changes; every edited fixture carries a "contract change" note:

- **#4 Mixed date-format semantics → fixed.** Bootstrap v2 migration (`PRAGMA user_version` 1→2, no schema change) normalizes stored `%m/%d/%Y` dates to ISO; POST/PUT `/api/mood` normalize the same format on write; garbage strings stay verbatim; stats SQL (incl. `_ISO_DAY_EXPR`) unchanged and now chronologically correct. - **#5/#6 Status-code consistency → fixed.** `GET /api/mood/{id}/selections` and `GET /api/goals/{id}/completions` (all alias paths) now 404 for nonexistent/foreign ids (`Entry not found` / `Not found`), matching their sibling GETs; an existing entry whose selections were cascade-deleted still returns 200 `[]`. `POST /api/groups/{id}/options` on an unknown/foreign group now 404s (`Group not found`) instead of 400. Frontend audited — no call site breaks.
- **#7 Goal update asymmetries → fixed.** Empty PUT/PATCH body → 400 `No fields to update`; blank/whitespace title → 400 `Title is required` (create's exact string); 404 now only means a missing/foreign goal.
