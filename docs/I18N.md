# Languages & translations (i18n)

This doc is for **self-hosters**: what Nightlio's language support does out
of the box, what (if anything) you need to configure, how a new language
reaches your instance, and how to run fully air-gapped. If you want to
**contribute a translation**, the contributor deep-dive — pack format,
plural rules, placeholders, the release pipeline — is
[`i18n/README.md`](../i18n/README.md).

## The default: bundled English, zero configuration

Nightlio ships its complete English catalog (`src/i18n/en.json`) inside the
frontend itself. Nothing needs to be configured, downloaded, or reachable:
a fresh instance runs fully in English with no network dependency at all,
and keeps doing so if GitHub is unreachable, the pack cache is cold, or
every i18n setting is left unset. Every other language is an *overlay* on
that catalog — any string a pack does not translate falls back to English,
so a partial or broken pack can never blank out the UI.

## How other languages arrive

Languages ship as **hot-swappable language packs**: standalone GitHub
releases tagged `lang-<code>-vX.Y.Z` (for example `lang-es-v1.0.0`) on the
repository named by `I18N_GITHUB_REPO` (default `FayedPatel/nightlio`).
`nightlio-api` discovers them at runtime — no app upgrade, no redeploy:

1. The api lists the repository's releases (at most once per
   `I18N_REFRESH_SECS`, default 3600 seconds, using conditional requests
   that don't count against GitHub's rate limit when nothing changed).
2. For each `lang-<code>-vX.Y.Z` tag it downloads the `<code>.json` release
   asset, validates it, and caches it both in memory and on disk next to
   the database (`<dir(DATABASE_PATH)>/i18n/`). The highest version per
   language wins.
3. `GET /api/i18n/languages` then lists the available languages, and the
   Settings → Language picker in the frontend shows them alongside bundled
   English. Picking one fetches `GET /api/i18n/{code}` and applies the pack
   immediately.

If a refresh ever fails, the api keeps serving whatever it already cached
(stale is better than nothing); if nothing is cached, the language list is
simply empty and everyone runs on bundled English.

## Adding a language (the short version)

The full contributor workflow lives in [`i18n/README.md`](../i18n/README.md);
end to end it is:

1. Author `i18n/packs/<code>.json` — a copy of `src/i18n/en.json` with the
   values translated, wrapped in the pack envelope. Partial translations
   are fine; untranslated strings stay English.
2. Validate locally: `yarn i18n:validate i18n/packs/<code>.json`
   (or `node scripts/validate-lang-pack.mjs i18n/packs/<code>.json`).
3. Open a PR with the pack file.
4. After the merge, a maintainer pushes the tag `lang-<code>-vX.Y.Z`. The
   [`i18n-release.yml`](../.github/workflows/i18n-release.yml) workflow
   validates, builds, and publishes the pack as a GitHub prerelease
   automatically.
5. Every running instance pointed at that repository discovers the new
   pack on its next refresh — within `I18N_REFRESH_SECS` (an hour by
   default), with no restart or redeploy.

Fixing a typo in an existing language — including English itself — is the
same flow with a bumped version tag.

## Air-gapped / offline instances

Two settings cover deployments that cannot (or should not) talk to GitHub
at runtime:

- **`I18N_LOCAL_DIR=<directory>`** — serve packs straight from a local
  directory of `<code>.json` files instead of GitHub. This takes precedence
  over discovery entirely: no network calls, no TTL, and edits to the files
  hot-swap strings on the next request without a restart. Build the files
  with `yarn i18n:build` / `scripts/build-lang-pack.mjs`, download them
  from the published releases, or write them by hand (the envelope shape is
  documented in `i18n/README.md`). In Docker, bind-mount the directory into
  the api container and point `I18N_LOCAL_DIR` at the container-side path.
- **`I18N_OFFLINE=1`** — keep the normal GitHub-backed mode but never
  fetch: the api serves only what its disk cache already holds. With a cold
  cache this means an empty language list — and bundled English still works
  for everyone, because it never depends on any of this.

## Configuration reference

All six variables are optional; unset (or empty — compose passes them
through empty-safe) means the defaults below. They are also listed in
[`SETUP.md`](SETUP.md)'s variable reference and documented inline in
`.env.example` / `.env.docker`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `I18N_GITHUB_REPO` | `FayedPatel/nightlio` | `owner/repo` whose `lang-<code>-vX.Y.Z` releases carry the packs. Point at your own fork/repo to curate your own set. |
| `I18N_GITHUB_API_BASE` | `https://api.github.com` | GitHub API base URL for release discovery (GitHub Enterprise, or a mock in tests). |
| `I18N_REFRESH_SECS` | `3600` | Seconds between discovery refreshes. Discovery is on-demand — no background polling. |
| `I18N_OFFLINE` | unset | `1` never contacts GitHub; serves only the existing disk cache. |
| `I18N_LOCAL_DIR` | unset | Directory of `<code>.json` packs served straight from disk; takes precedence over GitHub entirely. |
| `I18N_GITHUB_TOKEN` | unset | Optional token for the discovery calls (raises GitHub's unauthenticated 60 requests/hour API limit). |
